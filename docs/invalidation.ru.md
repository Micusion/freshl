# freshl — гайд по инвалидации

Как freshl решает, что убить и когда. Детали API — в
[api.ru.md](./api.ru.md); здесь — ментальная модель и рецепты.

## Три примитива инвалидации

| Примитив | Где объявляется | Убивает |
|---|---|---|
| **Ключ** | — | одну запись |
| **Тег** | `set(k, v, { tags: ['users'] })` | все записи с тегом |
| **Зависимость** | `set(k, v, { dependsOn: ... })` | саму запись, когда умирает её зависимость (транзитивно) |

Теги отвечают на вопрос *«о чём эти данные?»*. Зависимости — *«из чего эти
данные выведены?»*. Оба каскадируются, оба дёшевы: поиск идёт по обратным
индексам, а не полным сканированием.

## Рецепт: частичное обновление после мутации

Самый частый поток приложения — серверная мутация инвалидирует ровно то, что изменилось:

```js
const cache = createFreshl({ defaultPolicy: { ttl: 5000, swr: 30000 } });

// 1. загружаем каталог, помечаем тегом
cache.fetch('catalog', fetchCatalog, { tags: ['catalog'] });
cache.fetch('item:42', fetchItem, { tags: ['catalog'] });

// 2. объявляем событие один раз: resolve отображает payload → точные ключи
cache.bindEvent('item:restocked', {
  resolve: (payload) => ({ keys: payload.ids.map((id) => `item:${id}`) }),
});

// 3. после успешной мутации на сервере — эмитим с фактами
await api.restock(42);
cache.emit('item:restocked', { ids: [42] });
// → item:42 инвалидирован, catalog жив; ничего лишнего не перезагружается
```

Почему не весь тег? Можно и так — `invalidate({ tags: ['catalog'] })` — но тогда
каждая производная запись перезагрузится, даже если её входы не менялись.
`resolve`-правила держат инвалидацию хирургической.

## Рецепт: производные данные через зависимости

Если запись вычислена *из* других — объявите это, и каскад сделает работу:

```js
cache.set('user:1', user, { tags: ['users'] });
cache.set('profile:1', profile, { dependsOn: { tags: ['users'] } });
cache.set('feed', feed, { dependsOn: ['profile:1'] }); // цепочка, транзитивно

cache.invalidate({ tags: ['users'] });
// → ['user:1', 'profile:1', 'feed']
```

Каскад отключается, когда нужен только прямой хит:

```js
cache.invalidate('user:1', { cascade: false }); // profile:1 и feed выживают
```

## Рецепт: автообновление подписчиков

Третий столп — кто получает свежие данные. Свяжите подписку на инвалидацию с
перезагрузкой, и UI будет чинить себя после любого источника инвалидации:

```js
const rendered = new Set(['catalog', 'item:42']);

cache.on('invalidate', ({ keys }) => {
  for (const key of keys) {
    if (rendered.has(key)) cache.fetch(key, () => refetch(key)); // только то, что на экране
  }
});
```

Вместе с `resolve`-правилами получается: серверная мутация → одно событие →
хирургическая инвалидация → автоматический перезапрос ровно видимых записей.

## Взаимодействие с SWR

Инвалидация удаляет записи немедленно — стейл-но-пригодная запись остаётся
*живой*, пока её не инвалидировали. Два следствия:

1. Фоновая ревалидация, начавшаяся до инвалидации, **отбросит** свой результат
   (защита поколений) — мёртвая запись не воскреснет.
2. После инвалидации следующий `fetch()` — холодный промах; подписчики увидят
   `{ type: 'invalidate' }`, а затем `{ type: 'refresh' }` с приходом данных.

## Про `reason`

Каждая инвалидация несёт причину: `'manual'` по умолчанию, `'event:<имя>'` —
при срабатывании через `emit()`. Используйте её для маршрутизации подписчиков:

```js
cache.on('invalidate', ({ keys, reason }) => {
  if (reason === 'event:item:restocked') updateBadges(keys);
  else fullRerender(keys);
});
```

## Персистентность

Инвалидация удаляет и персистентную копию записи (адаптер получает `del(key)`),
поэтому перезагрузка страницы не может воскресить убитые данные. Полностью
протухшие записи отбрасываются при гидратации по той же причине.
